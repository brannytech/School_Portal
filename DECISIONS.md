# Implementation decisions

1. **Runnable local edition.** The project initially contained a Markdown specification, one standalone HTML masterclass, a PDF and school assets. A dependency-free Node 22 server and lightweight HTML/CSS/JavaScript client provide a working end-to-end local app immediately. This is a deliberate departure from the suggested Next.js/TypeScript/Tailwind, PostgreSQL/Prisma and NextAuth stack. There is no production deployment or claim of production readiness. The request concerns the existing local project; its server and private disk storage require a Node host rather than static Sites hosting.
2. **School branding.** `General.png` is the crest. The added building asset is actually named `sch_building.jpeg`; it is used on sign-in and registration. No substitute school photograph or generated branding is used.
3. **Academic scope.** 2026/2027 is the seeded session; first term starts current. All six classes and three terms are available. Only SS1 Mathematics first term is initially authored. Teachers can add course JSON for assigned subject/class/term combinations; empty curricula show a clear empty state. New sessions need a later model migration.
4. **Security lives on the server.** Role checks, active account status, class/subject scope, term/week locks, ownership of attachment records and private image access are rechecked for requests. Removing students preserves history and invalidates their access, including existing sessions. Passwords use salted scrypt. No public route serves the database, uploads or original unprotected masterclass.
5. **Local persistence.** Records use atomic JSON replacement, with bounded retries for transient Windows file locks. Uploaded photos are separate private files. Only one server process may use a database directory. Sessions are memory-only and expire in eight hours; signed viewing URLs last two minutes, upload tokens five minutes. Restart signs users out.
6. **Completion.** At least 60% of the 12 lesson practice questions must currently be correct, and reflection must be submitted. Quiz results do not substitute for the daily practice requirement. Re-answering a question updates that question’s result rather than inflating accuracy with repeated attempts.
7. **Maths quality.** The platform uses new generated and audited content rather than importing unverified answers from the existing HTML/PDF. The audit uses independent inverse/substitution methods and separately checks log tables. New teacher-authored content is structurally validated but is not automatically certified mathematically.
8. **Photo workflow.** Native camera capture plus gallery selection works without an in-app camera permission flow. The browser redraws and compresses pages; the server strips metadata too. No PDF, arbitrary document or video binaries are accepted by the image endpoint. Teachers may link HTTPS documents/videos. Notes and assignments are private; lesson-question photos and teacher lesson notes are shared with the class.
9. **Offline boundary.** A public shell is cached, not private student records. Failed/offline photos are held in a per-account queue on that browser/device. Recovery and final submission require an explicit student action after reconnecting, avoiding silent wrong-assignment submission. Shared devices should clear unused queued images.
10. **Demo honesty.** Names and scores are sample data. Live classes, videos and teacher lesson notes show empty states until a teacher adds real material. No fabricated meeting links, teacher endorsements, live sessions, or performance certifications are displayed.
11. **Milestones and verification.** This folder had no Git repository, so no artificial milestone commit history was created. Verification uses Node integration tests and a mathematical audit, plus browser checks. See the README for limitations and commands.
